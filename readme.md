# SuperRAID：FAT 驱动临时写缓存需求

## 本次工作范围

- 目标分支：`feature-fat`。
- 参考 `local` 分支中 `power-ctl/src/lib/cache_my_data.c`、fsctl 的 sysctl 调整及挂载恢复流程，以及下电相关实现。
- 本阶段实现 FAT32 驱动临时写缓存，不修改 fsctl 等用户态功能；不编写单元测试，以模块编译与隔离环境功能验证为准。
- 实现范围限定为 FAT32 定制驱动提供缓存开启、关闭能力。fsctl、libpowerctl 和 systemd service 仅作为需求背景与参考，本次不实现或修改其编排逻辑。
- 保持模块边界清晰、高内聚低耦合，不过度设计；未明确的行为需要先澄清。

## 产品场景与现有机制

产品运行在具有 A core / R core 的 SoC 上，参数存储使用 A/B 分区，通过哈希 footer 判断原始分区内容是否有效。

### 上电、挂载与恢复

1. 上电时由 `fsctl mount` 检查 A 分区；哈希一致则选择 A，否则检查 B，B 哈希一致则选择 B。按当前产品方案，非硬件故障情况下预期不会出现两侧都无效。
2. 选中的有效分区必须以 `rw` 方式挂载，使 APP 能正常读写。
3. 挂载完成后通过 `sd_notify` 通知服务就绪，使依赖参数挂载服务（需求中称 `app_param_mount.service`）的快速启动 APP 可以启动。从通知就绪开始，必须假设 APP 已经在读写。
4. fsctl 在通知就绪后继续检查对侧分区；如果对侧哈希不一致，需要把当前有效、已挂载分区的完整原始内容复制到对侧，完成备份恢复。
5. 恢复源必须保持为此前已经通过哈希 footer 校验的原始内容。恢复期间 APP 的写入可以被接收并被 APP 读取，但不能写入源分区的物理介质，不能破坏原始备份内容。

现有用户态方案在 APP 的 systemd 服务中预加载 `cachemydata`，使同步、直接写盘等操作不能触发预期的落盘行为；对可以缓存的写入，由 fsctl 调大若干 sysctl 缓存回写参数，以便在一定条件下暂留内存。具体拦截返回值、覆盖范围和回写条件，以 `local` 分支代码为准。

### 下电

1. R core 感知下电信号并通知 A core 中间件进入下电流程。
2. 中间件关闭 APP 后，通过 `local` 分支中的 libpowerctl 相关流程，经 D-Bus 通知 systemd reboot，进入 BSP 下电。
3. 已新增的 FAT 禁写 ioctl 预期由 libpowerctl 在下电流程使用：禁止写入、更新 A/B 哈希，并把已挂载分区内容同步到对侧。
4. 该禁写功能用于类似断电的写入关闭，与本次临时写缓存功能目的不同，两者应能配合工作。现有代码是否已完整实现上述产品流程，需要在分析中核对。

## 新增 FAT 功能要求

1. 通过 ioctl 开启和关闭临时写缓存，作用于对应的已挂载 FAT32 文件系统；不增加挂载参数或 mount 前独立控制接口。
2. 缓存开启期间保持 `rw` 和 APP 的正常读写；凡是将要写入磁盘的数据，都需要进入缓存，确保用于原始复制的底层分区内容不变。
3. 有实际写入时再按需创建缓存；不能仅依赖系统脏页回写参数来保证不落盘。
4. 关闭缓存时，将缓存中的内容刷到磁盘；完成后缓存退出后续正常读写路径中的实际工作，恢复通常的 FAT 行为。
5. 产品通常只在上电期间执行一次开启和关闭，但驱动能力应支持之后再次开启、关闭。
6. 需要覆盖数据及会改变原始分区内容的元数据写入，并分析同步写、直接 I/O、后台回写等路径，避免存在漏写到盘的路径。
7. 开启时机必须能保护已通过 footer 校验的原始内容。何时结束恢复并关闭缓存，由用户态决定；驱动不检查对侧恢复是否成功，也不负责校验哈希或操作对侧分区。

## 已确认的补充条件

- 缓存期间允许 `fsync`、`O_SYNC` 等同步操作成功，但仅保证数据进入内存缓存，暂不保证掉电持久化；关闭缓存时统一落盘。
- 本产品上电流程中，开启 ioctl 时 APP 尚未启动；关闭 ioctl 时 APP 可能正在写入。驱动仍需保留再次启停的能力，不能把首次开启的产品前提套用到所有调用。
- 用户已确认首次启用顺序为：`rw 挂载 → 开启缓存 ioctl 成功 → READY → APP 启动`。保留现有文件/目录 fd 控制方式，不增加挂载参数或 mount 前控制入口。驱动分析重点是开启、关闭期间的缓存维护，以及确认全部待回写内容落盘后才完成关闭。
- 关闭期间优先保持 APP 可以持续写入。仅在持续写入方案实现困难或不合理时，才考虑短暂阻塞；尚未同意在整个缓存刷盘阶段阻塞所有写入。
- A/B 分区实际各为 200 MiB，恢复期间预计最多为几 MiB 级别的修改；缓存内存预算可放宽至 GiB 级，但仍应按需分配，不预先分配整个分区或 GiB 级内存。
- 对侧恢复失败时，用户要求退出本次恢复，让 APP 在本次上电期间继续正常工作，后续在下电时由用户态完成对侧同步。这项策略由 fsctl 与 systemd service 等用户态逻辑负责，不属于驱动新增职责。
- 上述恢复失败策略意味着：如果用户态仍关闭缓存并回写源分区，而对侧尚无有效副本，则在源分区重新 seal 或对侧修复前异常掉电，可能失去最后一份 footer 校验有效的镜像。驱动的缓存关闭能力不提供 A/B 故障原子性保证。

## 待分析和澄清的边界

- 核对当前挂载流程至开启 ioctl 成功之间不产生破坏源镜像的 FAT 写入；首次开启依赖 APP 尚未启动，后续再次开启仍需协调已有修改和在途 I/O。
- 缓存期间直接 I/O 的处理方式、读后写一致性与底层原始读取的区别。
- 实际分配失败、关闭刷盘失败时的驱动行为；内存预算宽裕不等于分配一定成功。
- 关闭过程中持续写入的排序、同步边界，以及避免旧缓存覆盖新数据的方案。
- 开启、关闭与并发写入、卸载、下电禁写 ioctl 的协调；恢复尚未完成时的产品下电编排留在用户态。

除已确认条件外，上述边界尚未确定实现决策；先依据两个分支的实际代码分析最小方案，再确认必要的产品语义。

## 关闭过程的分析约束（尚非已实现方案）

- 进入排空阶段不等于缓存已经关闭；关闭 ioctl 只有在规定同步边界内的数据、元数据和缓存回写全部成功，并完成必要设备 flush 后才能报告成功。
- 优先分析“正常、缓存、排空”三个内部状态。排空期间仍协调读写，但逐步将新写入转入正常路径，不能在 APP 持续写入时无限追加新的延迟缓存任务。
- 同一块的新写入必须与旧缓存回写有序衔接，禁止旧内容在新内容之后覆盖磁盘；无冲突的写入无需等待整个缓存排空。
- 空缓存容器不是充分的完成条件：还需要处理在途缓存生产者、已提交未完成的 I/O、切换前的普通脏页和元数据缓冲，以及仍在引用缓存的读取者。
- 切换后的普通 buffered write 恢复 FAT 正常语义；不能以“并发 APP 不再产生任何脏页”作为关闭完成条件。
- 回写或设备 flush 失败必须向调用者报告，不能假装已成功关闭；保留必要的未完成数据和错误状态。已经开始回写后不再保证旧源镜像不变。
